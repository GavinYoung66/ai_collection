# 第一部分 · 整体规划

## 1. 背景与定位

**现状痛点**：三个业务服务曾各自托管一个演示页（complaint-service/web、qc-service/web、rag-service 的 Gradio 工作台），彼此割裂无统一入口，且完全缺失鉴权——任何人可直接访问后端接口。没有可复用的前端底座，后续每做一个业务模块都得从工程初始化、请求封装、布局骨架重抄一遍。（三个演示页已于 2026-10-25 全部下线删除，本前端为唯一入口，见附录 B v1.12）

**定位**：统一管理台，一次立好底座（登录 + 鉴权 + 请求链路 + 布局骨架），后续业务模块以「加目录 + 加路由 + 加菜单配置」的方式长入，不动底座。

**前端在整体系统中的位置**（前端不直连任何后端服务，全部经 Nginx 网关）：

```
浏览器（Vue SPA，本工程）
   │  所有 /api 请求
   ▼
Nginx 网关（:8080，开发态经 vite proxy 转发，生产态同源托管 /admin/）
   ├── /api/v1/auth/login|me ──► auth-sidecar（JWT 签发 / 当前用户，豁免 ENABLE_AUTH）
   ├── /api/v1/complaints/*  ──► complaint-service（F1）
   ├── /api/v1/qc/*          ──► qc-service（F2）
   ├── /api/v1/kb/*、/api/v1/sensitive-words/* ──► rag-service（F2）
   └── /api/v1/llm-usage/*   ──►（F3 新增端点，数据落 llm_call_logs 表）

未纳入本期管理台（不在本文档范围）：
   call-service / case-service / review-service（骨架占位，各 6 个 py 文件）
   data-platform（后端内部数据同步服务，无独立 UI）
   mcp-gateway（MCP 协议网关，无 UI）
```

后端事实约束（前端设计不得违背）：统一响应信封 `{code, message, data, trace_id}`；JWT 由 `common/security/rbac.py` 签发；User 模型 5 种角色字符串（admin/supervisor/agent/qc_reviewer/ai_trainer）；`X-Trace-Id` 请求头透传由 `common/trace/middleware.py` 支持（见 §9.4）。

## 2. 设计目标与原则

| 原则 | 落地手段 |
|---|---|
| 解耦 | 业务模块放 `modules/`，共享能力放 `shared/`，模块间禁止互相 import |
| 可扩展 | 新增模块 = 加目录 + 加路由 + 加菜单配置，不动底座 |
| 稳定 | 统一请求封装/信封解包/错误处理/三态规范，所有模块共用一条链路 |
| 好迭代 | 分层依赖单向化 + TypeScript 全覆盖 + Vitest 关键路径守护 |

## 5. 模块功能规划（F0 ~ P1）

> 本节所有端点以 **§5.0 端点契约基线** 为唯一事实源；功能树中的路径均为经 Nginx 网关访问的绝对路径，禁止省略 `/api/v1` 前缀。

### 5.0 端点契约基线（唯一事实源）

> **证据约定**：路径/方法逐条取自后端源码（`services/<svc>/app/**`，行号为当前代码行）。网关 `proxy_pass` 不带 URI，**路径原样透传，不存在重写**，因此表中路径即后端真实路由。
> **契约所有权**：本表是后端路由的**镜像**，不是前端独立定义。后端新增/修改/删除路由时，本表随之失效；前端不得为了"好写"而改写路径、方法或包一层自定义别名。
> **维护规则**：后端新增/变更路由时，必须同步本表；F1/F2/F3 各期退出标准包含「本表逐条 method + path 对照通过」。禁止再从旧演示页菜单反推端点。

**契约派生关系（前端每类产物只能有一个来源）**

| 前端产物 | 唯一来源 | 核对方式 |
|---|---|---|
| `modules/<biz>/api.ts` 的 path / method / 入参 | 各服务 FastAPI 路由 + Pydantic schema | 各服务 `/openapi.json`，逐条比对 §5.0 |
| `modules/<biz>/types.ts` interface | Pydantic schema（字段名、可选性、枚举取值） | `/openapi.json` → `components.schemas` |
| `shared/utils/error-map.ts` | `common/errors/codes.py` 的 `ErrorCode` 与 `ERROR_MESSAGES` | 直接对照源码，**禁止前端新增错误码** |
| `shared/request.ts` 的 `TIMEOUT` 常量 | `deploy/gateway/server_common.conf.template` 的 `proxy_read_timeout` | 按 §9.3 矩阵，前端值必须更小 |
| `Role` 类型 | `common/db/models/user.py`（**5 种角色字符串，唯一枚举来源**） | 逐字比对 `role` 列 comment 与 `status` 列，禁止增删角色；`seed_users.py` **不是**角色来源（当前仅覆盖 3 种，见 §3.2 注） |
| 路由 `meta.roles` | 本文 §3.2 产品矩阵（业务可见性决策） | 角色名必须落在后端 5 种角色之内 |

> 判据一句话：**凡是"前端改了、后端没改"就能生效的契约字段，都是错的**——说明它是前端单方面发明的。

**A.1 认证契约（F0 冻结，前后端唯一依据）**

> 后端已实现（`deploy/auth/main.py`），网关经 `location /api/v1/auth` 原样透传；该 location **不挂 `auth_request`**。响应信封与各服务一致，**成功码为 int `0`**（对齐 complaint 口径）。

```jsonc
// POST /api/v1/auth/login 请求体
{ "username": "admin", "password": "Admin@2026" }

// 成功 HTTP 200
{
  "code": 0,
  "message": "ok",
  "data": {
    "access_token": "<JWT>",
    "token_type": "bearer",
    "expires_in": 86400,
    "user": {
      "user_id": "<uuid>",
      "username": "admin",
      "real_name": "系统管理员",
      "role": "admin",
      "status": "active"
    }
  },
  "trace_id": "<32位hex>"
}
```

| 项 | 规则（后端事实） |
|---|---|
| 登录入参 | `username`（1~50 字符）、`password`（1~128 字符），JSON |
| 当前用户 | `GET /api/v1/auth/me` 携带 `Authorization: Bearer <token>`，`data` 为单个 `user` 对象（字段同上） |
| JWT 载荷 | `sub`=user_id、`role`=5 种规范角色值、`exp`；有效期 `JWT_EXPIRE_HOURS`（默认 24h），`expires_in` 为秒数 |
| 凭证错误 | HTTP 401 + `B0002` + `message="用户名或密码错误"` |
| 账号停用/锁定 | HTTP 403 + `B0003` + `message="账号已停用或锁定"` |
| token 无效/缺失 | HTTP 401 + `B0002` + `message="请先登录"` |
| 入参校验失败 | HTTP 422 + `B0001`（无字段级明细，前端自行 rules） |
| 刷新机制 | **无 refresh token**：401 即清登录态重新登录 |
| 角色来源 | `/me` 以**数据库当前 role/status** 为准，token 内 role 仅作鉴权旁路；权限回收后最长一个请求周期内生效 |

> 前端落地：token 存 auth store（唯一 localStorage 读写点，见 §9.1/§10）；`fetchMe()` 用 `/me` 重建 userinfo；**禁止前端解析 JWT**（角色、过期时间一律以 `/me` 与 401 为准）。

> 说明：JWT 的 `role` 声明取自 `common/db/models/user.py` 定义的 5 种规范值（admin / supervisor / agent / qc_reviewer / ai_trainer）；`scripts/seed/seed_users.py` 已覆盖全部 5 种（见 §3.2 注）。下表 allowlist 是各服务**源码字面值**，比对方式为**大小写不敏感的全等匹配**（`qc-service/app/auth.py:55-80`、`rag-service/app/services/require_role.py:45-70`），**不存在别名映射**。

|---|---|---|---|

### 5.0.1 后端统一交互规范（前端必须逐条遵守）

> 本节是从后端代码提炼的**统一规则**，前端请求层、API 层、类型层必须完全照此实现。规则有疑问或与前端直觉冲突时，**改前端，不改契约**；确认后端规则本身有缺陷时，提给后端修，前端不得私自绕过。

**1）响应信封与 HTTP 状态**

| 规则 | 后端事实 | 前端做法 |
|---|---|---|
| 信封结构 | `{code, message, data, trace_id}`（统一异常处理器 `common/errors/handlers.py`） | 拦截器统一解包，业务代码只见 `data` |
| 成功判定 | **只看信封 `code`**：统一走 `isSuccess(code)`（`0` 或 `"0"`）。HTTP 状态只表达传输层 | 先解包、再按 `code` 分支；**禁止 `if (status === 200) return data`** |
| 业务失败的 HTTP 状态 | **各服务不一致**：complaint 路由用 `fail()` 直接返回 dict → **HTTP 200** + `code:"A5xxx"`（`api/response.py:27-45`）；qc 按 `HTTP_STATUS_BY_CODE`（A2001/A2003/A2009/A2010/A2011→200，A2004/A2008→400，A2005/A2007→404，A2006→409，A2002→422；`qc/app/errors.py:14-29`）；rag 走 `BizException` → 400 | 一律按 `code` 走 §15.1 白名单；HTTP 状态仅用于网络/网关诊断，不参与业务成败判定 |
| 业务异常（`BizException`） | HTTP **400** + `A5xxx/B000x/B0004`（`handlers.py:15-22`） | 400 不是"请求坏了"，按信封解析并走错误码白名单 |
| 参数校验失败 | HTTP **422** + `B0001` + 固定文案「参数校验失败」，**不含字段级明细**（`handlers.py:33-40`）；qc 服务例外用 `A2002`（`qc/app/errors.py:16`，明确不叠 B0001） | 前端必须自己完成字段校验（Element Plus `rules`），不得依赖后端返回哪个字段错 |
| 系统异常 | HTTP 500 + `B0007` | 兜底提示 + trace_id |
| 网关错误 | 401 `B0002`、429 `B0006`、502 `B0008`、504 `B0009`，**均带信封**（`server_common.conf.template:222-260`） | 所有状态码先按信封解析，再分支处理 |
| 限流 | 429 + `B0006` + 响应头 `Retry-After` | 读 `Retry-After` 退避，不盲目立刻重试 |

> **D1（成功码类型）**：complaint 与 auth-sidecar 为 int `0`，qc/rag 为 str `"0"`。前端 `isSuccess()` 同时兼容；后端统一为 int `0` 后收紧为单值并更新本节。

**非信封端点白名单（唯一例外，新增必须登记）**

| 端点 | 实际响应 | 前端处理 |
|---|---|---|
| `GET /api/v1/sensitive-words/current.dict` | `text/plain` 原始词典；异常为 `HTTPException(404, {"detail": ...})`（`sensitive_words.py:27-45`） | 走 `request.getText()`（同一 axios 实例，`responseType:'text'`），跳过信封解析；404 视为「词典为空」空态，**不报系统错误** |

> 除上表外，所有接口一律按信封解析。若后端新增非信封端点，必须先登记本表并同步 §9.1 例外分支。

**2）分页契约（列表页统一）**

| 项 | 规则 | 证据 |
|---|---|---|
| 请求参数 | `page`（从 **1** 开始，`ge=1`）、`page_size`（默认 **20**，上限 **100**，`le=100`） | `complaints.py:89-90`、`qc/records.py:116-117` |
| 响应结构 | `{ items, total, page, page_size }` | `complaints.py:104-107`、`qc/records.py:152-155` |
| 前端约束 | 禁止传 `page=0`、禁止 `page_size>100`；`PageTable` 的默认值必须与后端一致 | — |

**3）字段命名与数据格式（禁止前端自行转换）**

| 项 | 规则 |
|---|---|
| 字段命名 | 请求/响应全为 **snake_case**（如 `page_size`、`complaint_id`）；前端**禁止**自动 camelCase 转换，interface 字段名与后端逐字一致 |
| 主键 | **UUID 字符串**（如 `{complaint_id}`、`{session_id}`、`{doc_id}`），前端一律按 string 处理，不做数值化 |
| 时间 | 后端 `model_dump(mode="json")` 输出 **ISO 8601 字符串**；前端按字符串透传，展示层格式化，不做隐式时区改写 |
| 枚举 | 与后端 Enum 取值逐字一致（如 `task_status`、`verdict`）；前端类型用字符串字面量联合，禁止自造中文枚举值 |
| 空值 | 后端可选字段为 `null`；前端禁止把 `null` 当 `undefined` 或空字符串处理 |
| 请求体 | JSON 为 `application/json`；上传为 `multipart/form-data`（字段名以后端 `UploadFile` 参数名为准） |

**4）认证与追踪头**

| 头 | 方向 | 规则 |
|---|---|---|
| `Authorization: Bearer <token>` | 前端 → 后端 | 唯一注入点 `shared/request.ts`；token 为空不注入 |
| `X-Trace-Id` | 双向 | 前端可传（复用当前操作链路）；后端无则生成、并在响应头回传（`common/trace/middleware.py:22-26`）；网关/侧车错误体 `trace_id` 取自 `$trace_id` |
| `X-User-Id` / `X-User-Role` | 网关 → 后端 | 由 auth_request 注入，**前端禁止伪造**（伪造无效且属越权） |

**5）前端禁止行为（对应 §18）**

- 禁止把 snake_case 自动转 camelCase，或反向转换后再发送
- 禁止以 HTTP 状态判定业务成败（如 `status === 200` 即成功）；complaint 的业务失败就是 HTTP 200 + 非 0 `code`
- 禁止在业务代码里自行拼 `code` 判断成功（如只判 `code === 0`），必须走统一 `isSuccess()` 工具（兼容 D1）
- 禁止依赖后端返回字段级校验错误（它不返回）
- 禁止自造分页参数名（`limit/offset/current/size` 一律不允许）
- 禁止绕过 `shared/request` 直接 `fetch`/新建 axios 实例
- 禁止用 `data` 之外的字段（如 `result`、`rows`）承载列表数据

> **给前端同学的后端概念对照**：`信封` = 后端所有接口的统一返回外壳；`trace_id` = 一次请求的全链路身份证（排障时拿它查后端日志/Langfuse）；`幂等` = 重复提交不会产生两条数据（前端仍需按钮防重）；`限流` = 后端按频率拒绝（429/B0006）；`服务` = 后端按业务拆的独立进程，前端只认网关一个入口。

> **后端待统一缺陷（D1）**：成功码类型不一致（int `0` vs str `"0"`）。规范建议统一为 **int 0**（complaint `response.py` 已注释「成功：code 为 int 0」）。修复前前端用 `isSuccess()` 兼容两种；修复后收紧为单值并更新本节。

## 7. 总体分层与模块契约

```
┌──────────────────────────────────────────────────────────┐
│ 业务模块  modules/<biz>/                                  │  自包含：routes/api/types/store/views/components
│           complaint | qc | rag | usage | system           │  只依赖 shared，禁止依赖其他模块
├──────────────────────────────────────────────────────────┤
│ 公共能力  shared/                                         │  无业务语义：request / envelope 类型 /
│           request、types、components/base、composables、utils│  基础组件、组合式函数、错误码映射
├──────────────────────────────────────────────────────────┤
│ 底座（壳）app/                                            │  装配、布局、登录、错误页、全局样式
│           main、router（汇总）、layouts、pages、styles     │  不含任何具体业务页面
└──────────────────────────────────────────────────────────┘
                 ▲ 唯一装配方向：app/router → modules → shared
```

铁律（违反即 CI 失败）：

1. **`modules/A` 不得 import `modules/B` 的任何文件**（含类型、组件、store）。需要共享 → 下沉 `shared/`
2. `modules/*` 只能依赖 `shared/`、Vue、Element Plus、ECharts 等第三方库；不得 import `app/`
3. `shared/` 不得 import `modules/` 或 `app/`；`shared/` 内不得出现业务名词（complaint/qc/rag 等）
4. **`app/router/index.ts` 是唯一装配点**（composition root），允许 import 各模块的 `index.ts`；`app/` 其他文件不得 import 模块内部文件
5. 每个模块的 `api.ts` 是访问后端的**唯一入口**，且只能调 `shared/request`；禁止 `fetch`、禁止新建 axios 实例
6. `api.ts` 不得 import Element Plus / Vue 组件；`store.ts` 不得直接操作 `localStorage`（统一走 auth store）
7. 跨模块复用的组件/类型，先下沉 `shared/` 再使用；**禁止通过深路径 `modules/A/views/X.vue` 引用**

### 7.1 业务模块契约（每个模块必须满足）

```
modules/<biz>/
├── index.ts      # 唯一出口：导出 BizModule（name + routes），外部只准 import 这一个文件
├── routes.ts     # RouteRecordRaw[]，每条必须带 meta.title/icon/roles
├── api.ts        # 该模块全部后端调用，只调 shared/request
├── types.ts      # 该模块专属类型，字段名与后端 Pydantic 逐字一致（snake_case）
├── store.ts      # 可选：模块级 Pinia store（跨页面共享时才建）
├── views/        # 页面级组件（路由直接挂载）
└── components/   # 模块内组件，禁止外部引用
```

```ts
// modules/<biz>/index.ts —— 模块契约
import type { RouteRecordRaw } from 'vue-router'

export interface BizModule {
  name: 'complaint' | 'qc' | 'rag' | 'usage' | 'system'
  routes: RouteRecordRaw[]
  setup?: () => void        // 可选：模块级副作用（极少用；默认不写）
}

const bizModule: BizModule = { name: 'complaint', routes }
export default bizModule
```

> 契约的目的：**删掉一个业务模块 = 删一个目录 + 删 `router/index.ts` 里一行 import**，其余代码零改动、无孤儿引用。这与后端「一个服务一个目录」完全同构。

### 7.2 边界强制手段（不靠自觉，靠工具）

| 手段 | 配置 | 作用 |
|---|---|---|
| ESLint 限制深链 | `no-restricted-imports` 禁止 `@/modules/*/views/*`、`@/modules/*/components/*` 等非 `index.ts` 路径 | 杜绝绕过模块出口 |
| 依赖图校验 | `dependency-cruiser`：禁 `modules/A→modules/B`、`shared→modules`、`modules→app`；禁非 `app/main.ts` → `mocks/` | 机器判定分层是否被破坏 |
| CI 门禁 | 现有 `frontend` job 追加 `depcruise src` | 破坏分层直接红 |
| **可插拔验证** | 删除 `modules/<biz>` + `router/index.ts` 一行 → `vue-tsc --noEmit && vite build` 必须通过 | 证明模块真的可拔，不是口头可插拔 |

### 7.3 变更影响面（底座稳定的度量）

| 变更类型 | 允许改动的范围 | 必须回归的范围 |
|---|---|---|
| 新增业务模块 | `modules/<biz>/` + `router/index.ts` 一行 | 该模块自身 |
| 修改请求层/信封 | `shared/request.ts` | **全模块**（跑全量 Vitest + 冒烟） |
| 调整角色可见性 | 该模块 `routes.ts` 的 `meta.roles` + 本文 §3.2 | 菜单快照测试 |
| 后端接口变更 | 该模块 `api.ts`/`types.ts` + §5.0 契约表 | 该模块 + 契约对照 |
| 改布局/壳 | `app/` | 全模块（仅视觉回归） |

> 判据：**改动一个业务模块，不应要求改 `shared/` 或 `app/`**；若必须改，说明该能力本应下沉公共层，或模块边界划错了。

## 9. 请求层设计（全工程命脉，先定死）

### 9.1 唯一 axios 实例（shared/request.ts）

- 请求拦截器：注入 `Authorization: Bearer <token>`（token 由 auth store 在 `initFromStorage / login / logout` 时写入 `shared/request.ts` 暴露的模块级 token holder，拦截器只读该 holder；**`shared/` 不得 import `app/`**，否则形成 `auth store → api → request → auth store` 循环；**auth store 是唯一 localStorage 读写点（key `ac_token`），`request.ts` 只持内存 token、不读写存储**；token 为空不注入）
- 响应拦截器（**所有 HTTP 状态码统一按信封解析**，因为网关 401/429/502/504 也返回信封，见 §5.0.1）：
  0. **非信封白名单例外**：仅 `GET /api/v1/sensitive-words/current.dict`（§5.0.1 白名单）走 `responseType:'text'`，直接返回字符串，不进入下述信封解析；其 404 映射为空态
  1. 解析 body 是否为 `{code,message,data,trace_id}`；是信封则进入业务分支，不是信封则按网络/网关异常兜底
  2. 成功判定统一走 `isSuccess(code)`：`code === 0 || code === "0"`（兼容 D1，收敛后改为单值）→ 解包返回 `data`
  3. `401` 或 `B0002` → 清空 auth → 跳 `/login?redirect=当前路由`（**先清登录态**，防止后续请求继续带过期 token）；**例外：`POST /api/v1/auth/login` 自身的 401 只做表单提示，不清态、不跳转**（否则登录页自跳死循环）
  4. `429` 或 `B0006` → 读响应头 `Retry-After`，提示并计算退避时长；**拦截器不自动重试**（重试只由调用方按 §15.1 执行，且仅幂等 GET）
  5. `422`（`B0001` 或 qc 的 `A2002`）→ 表单校验失败：后端无字段级明细，统一提示「请检查输入」，具体标红由页面 `rules` 承担
  6. 其他非成功 code → 先查 `error-map.ts` 白名单（§15.1），未命中则 message 直出 + trace_id 后 8 位 → reject
  7. 无信封（超时/连接中断/非 JSON）→ 兜底提示，trace_id 显示「无」
- 所有 API 函数返回 `data` 的强类型，业务代码永远见不到信封；业务代码也不得自行判断 `code`

### 9.2 环境接入

- 开发态：`vite.config.ts` 配 `server.proxy`，`/api` → `http://localhost:8080`（Nginx 网关），不引入新 CORS 面；proxy 到网关而非直连后端，保证 dev/prod 请求路径完全一致
- 生产态：`vite build` 产物由 Nginx 同源托管 `/admin/`；`base: '/admin/'` 从 F0 起即固定（开发态入口相应为 `http://localhost:5173/admin/`），F4 只改托管与 ENABLE_AUTH，不再改构建配置
- **base 三处必须同源**：`vite.config.ts` 的 `base`、路由 `createRouter({ history: createWebHistory(import.meta.env.BASE_URL) })`、Nginx 托管前缀 `/admin/`。漏掉 router history 会导致刷新深链（如 `/admin/complaints/:id`）匹配不到路由而 404，属 F0 验收项
- axios 的 `baseURL` 取 `import.meta.env.VITE_API_BASE`，**F0 起固定为空字符串**：api 层一律按 §5.0 契约基线写根绝对路径 `/api/v1/...`（禁止省略 `/api/v1` 前缀），空 baseURL 下即解析为同源 `/api/v1/...`；与 SPA base **解耦**，禁止拼成 `/admin/api` 或 `/api/api`。开发态由 vite proxy 把 `/api` 转发到 `http://localhost:8080`（网关），生产态同源直连网关。若后续改回 `VITE_API_BASE=/api`，则 api 层路径必须同步去掉 `/api` 前缀（`/v1/...`），且 `request.ts` 的登录自身 401 匹配串需一并调整，二者必须成对修改

### 9.3 超时矩阵（硬约束：前端必须小于网关）

超时只有一张来源表，业务代码禁止散写 `timeout` 数值。铁律：**前端超时 < 网关 `proxy_read_timeout`**，否则网关先掐断、前端仍在等，错误会被误判成“网络异常”。

| 场景 | 网关 read_timeout | 前端 timeout | 说明 |
|---|---|---|---|
| 普通请求（`/api/v1/complaints`、`/api/v1/qc`、`/api/v1/kb` 默认） | 15s | **12s** | 留 3s 余量，保证前端先失败、能给出可解释提示 |
| 研判触发 `POST /api/v1/complaints/{id}/judge` | **120s**（专用正则 location） | **110s** | 唯一已放宽的长任务端点 |
| RAG 在线问答 `POST /api/v1/kb/search`（`answer=true`） | 15s（现状） | **暂不实现** | F2b 阻塞依赖：后端加 120s location 后前端按 110s；否则必 504 且 trace 断链 |
| 文档上传 `POST /api/v1/kb/documents` | 15s（现状） | **12s** | 异步入库后响应即时（仅校验+落库，`documents.py:66`），网关 15s 读超时不再构成瓶颈；请求体上限 `client_max_body_size 100m`（`nginx.conf.template:11`）；原「需放宽至 60s+」阻塞依赖 **v1.6 解除** |
| QC 回放 `POST /api/v1/qc/replay/*`（含 replay/raw 与 replay/{session_id}） | **120s**（专用正则 location `^/api/v1/qc/replay/`，照 judge 先例） | **110s**（`TIMEOUT.qcReplay`） | 同步含 LLM 复核（后端硬超时 5s），最坏 ≈9s；v1.4 闭环，原 15s 误杀 504 风险消除 |
| QC 批量质检 `POST /api/v1/qc/check/batch` | **120s**（专用正则 location `^/api/v1/qc/check/batch$`） | **110s**（`TIMEOUT.qcReplay`） | 串行循环，前端勾选上限 10 条（最坏 ≈90s < 110s，留 20s 余量）；大批量走后端异步（P1） |

实现方式：`shared/request.ts` 内维护 `TIMEOUT` 常量表（`normal: 12_000`、`judge: 110_000`、`qcReplay: 110_000`），api 层按端点引用常量——**不派生第二 axios 实例**，拦截器/信封/错误处理始终只有一份。**上传永久沿用 `normal`，不设 `upload` 独立常量**（v1.6：异步入库后原放宽需求解除）。

### 9.4 X-Trace-Id 透传约定

- 后端 `common/trace/middleware.py` 已支持：请求带 `X-Trace-Id` 则沿用，无则生成 uuid，并在响应头回传
- 前端约定：请求拦截器从模块级 trace 上下文读取「当前 trace_id」并注入请求头；需要串联「用户查看→发起操作」复合链路时（如 F1 投诉详情页内一连串操作），由对应 store/composable 写入 trace 上下文
- 响应侧：拦截器统一从响应头 `X-Trace-Id` 与信封 `trace_id` 取同一个值（优先响应头），错误提示附后 8 位
- F0 期仅留扩展点，不启用；F1 投诉详情页落地
- 业务代码禁止手写 `X-Trace-Id` 头，统一走拦截器

## 10. 状态设计

| 状态 | 位置 | 理由 |
|---|---|---|
| token / userinfo / role | `app/stores/auth.ts` | 跨会话保持登录；刷新后 `fetchMe` 重建 userinfo。**auth store 是唯一 localStorage 读写点（key `ac_token`）**，`shared/request.ts` 只持内存 token |
| 列表查询条件/分页 | 组件本地（`useTable` 管理） | 无跨页面共享需求，进 store 是负担 |
| 跨页面共享数据（如投诉详情页跳转带参） | 路由 params/query | URL 可分享可刷新，优于 store 传值 |
| 全局 UI（侧栏折叠） | `app/stores/app.ts` | 真全局 |

auth store 契约：

```ts
interface AuthState {
  token: string | null            // 持久化到 localStorage（key: ac_token）
  user: UserInfo | null           // { user_id, username, real_name, role, status }
  role: Role | null               // user?.role，不单独持久化
  loaded: boolean                 // 首屏是否已完成 /me 引导
}
// actions: login(u, p) / logout() / fetchMe() / ensureLoaded() / hasRole(...roles)
```

初始化时序：`setup()` 阶段先 `initFromStorage()`（读 localStorage），有 token 才调 `fetchMe()` 重建 userinfo——token 过期会触发 401，由 axios 拦截器自动清空 + 跳登录。username/role 不持久化：必须由 `fetchMe()` 从服务端拉取，防御"admin 权限被回收但 token 未过期"的边界。
`ensureLoaded()`：`loaded === true` 直接返回；否则复用同一个 in-flight Promise（并发路由跳转只发一次 `/me`），失败时清空登录态并抛出，由守卫统一跳登录。

## 11. 路由与权限机制

- 每个模块在 `modules/<biz>/routes.ts` 导出 `RouteRecordRaw[]`，经 `modules/<biz>/index.ts` 暴露为 `BizModule`；`app/router/index.ts` 汇总各 `BizModule.routes`（唯一装配点，见 §7.1）
- `meta.roles?: Role[]` 声明可见角色（矩阵见 §3.2），缺省 = 登录即可见；`meta.title/icon` 驱动菜单与面包屑
- 全局前置守卫顺序：① `await auth.ensureLoaded()`（首屏 token 存在但 userinfo 为空时调 `/me`，**in-flight 去重**，失败即清态跳登录）；② 未登录 → `/login?redirect=`；③ 已登录但角色不在 `meta.roles` → `/403`
- **role 为空时禁止计算重定向**：`firstAccessibleRoute(role)` 仅在 role 为 5 种规范值之一时才执行；返回空则落 `/403`。`/403`、`/login`、404 通配三条路由不参与该计算，避免 `/` ↔ `/403` 互跳成死循环
- `/me` 返回 401 时由 axios 拦截器统一清态跳登录，守卫不得再次跳转（防止双跳）
- 侧边栏菜单由同一份路由表驱动，菜单过滤与路由拦截共用一份 `meta`，不会出现「菜单藏了但前端路由能进」的不一致

**权限边界声明（必读）**：`meta.roles` 与路由守卫是**可见性与体验约束**，不是安全边界——前端代码可被篡改，路由拦截不能阻止直接调用 API。真正的接口级鉴权必须由后端保证：当前后端已具备「认证」（token 有效性校验）；「角色级授权」仅部分覆盖（`deploy/auth` 的 `/internal/authz`），完整角色鉴权列为 P1 后端待补项。前端不得以任何形式承担授权职责，也不得把敏感数据仅靠菜单隐藏来保护。

> **取舍说明**：路由采用编译期静态 import 各模块的 `index.ts`，换取完整 TypeScript 类型提示与最简装配；**不采用**运行时 `addRoute` 动态注册/卸载——工程体量小（≤6 个模块），新增模块只需一次 import，运行时插拔属过度工程。**"可插拔"在本项目的定义 = 编译期可增删（删目录 + 删一行），不是运行时热插拔**。

## 12. 组件拆分规范

- **容器组件**（模块 `views/`）：管数据获取、状态、交互编排；不写样式细节
- **展示组件**（模块 `components/`）：props 进、emit 出，不碰 store 和 api
- 公共组件统一放 `shared/components/base/`（**无业务语义**），业务组件留在各模块内
- Element Plus 二次封装只封这四个（足够覆盖 90% 场景，不滥封）：
  1. `PageTable`：查询表单 + 表格 + 分页三合一（所有列表页复用，分页参数默认值对齐 §5.0.1）
  2. `DetailDrawer`：详情抽屉壳（标题/加载态/操作区插槽）
  3. `StatusTag`：统一状态枚举 → 颜色/文案映射
  4. `TraceIdText`：trace_id 展示 + 一键复制（排障串联用）
- **AI 域组件沉淀方向**（不定契约、F0 不预建目录）：F1 起，跨**模块**复用的 AI 域组件（如 Agent 链路卡、RAG 召回预览卡）沉淀至 `shared/components/ai/`，一律 props 传入、不硬编码催收业务字段；**模块内自用的不要下沉**；待第二个真实使用者出现时再下沉，防止凭空设计

## 13. 类型策略

- 手写 interface 对齐后端 Pydantic schema：**模块专属类型放 `modules/<biz>/types.ts`**，跨模块通用类型（信封、分页、Role）放 `shared/types/`；**字段名与后端逐字一致（snake_case），禁止 camelCase 转换**
- 统一泛型：`ApiEnvelope<T> = { code: number | string; message: string; data: T; trace_id: string }`（`code` 兼容 D1）；`PageResult<T> = { items: T[]; total: number; page: number; page_size: number }`（与后端分页响应逐字段一致，见 §5.0.1）
- 基础类型约定：主键 `string`（UUID）、时间 `string`（ISO 8601，透传不转换）、可空字段 `T | null`（不用 `undefined` 兜底）、枚举用字符串字面量联合
- 后端 schema 变更时以编译错误为信号逐点修正——**不引入代码生成器**（现阶段接口量可控，生成器是过度工程）
- **契约漂移检测**：CI 增加一步导出各服务 `/openapi.json` 快照并与基线 diff，有变更即告警（不阻断合并，阻断“无人知晓的静默变更”）；同步核对 §5.0 契约表，这是手写 interface 方案的必要补丁
- `Role` 枚举与后端 `user.py` 的 5 种字符串严格一致（**以 `user.py` 为唯一来源**；`seed_users.py` 仅提供测试账号，目前覆盖 3 种，缺 qc_reviewer / ai_trainer，见 §3.2 注）

## 14. 实时性选型

| 场景 | 方案 | 理由 |
|---|---|---|
| 投诉研判进度（LangGraph 节点推进） | 轮询 `GET /api/v1/complaints/{id}/status`，`usePolling` 封装 | 后端无推送通道；status 是轻量端点，不带 evidence 组装 |
| 质检告警流 | 进页拉取 + 手动刷新 | 非高频场景 |
| 后续若需服务端推送 | 再评估 SSE | 不提前建设 |

### 14.1 轮询契约（`usePolling` 必须满足）

1. **端点**：只轮询轻量状态端点 `/status`，禁止轮询详情 `/complaints/{id}`（详情含证据组装，成本高）。到达终态后再拉一次 `/verdict` 与 `/agent-logs` 补齐展示。
2. **节奏**：首轮 3s；连续 20s 状态无变化退避到 5s，上限 10s；禁止固定高频轰炸。
3. **终态判定**：`task_status ∈ {resolved, closed, archived}` 立即停止（枚举对齐 `app/models/state.py`）；`pending_review / pending_senior_review / pending_callback` 属「等待人工」，由页面决定继续低频轮询或停止并提示。
4. **页面可见性**：`document.hidden` 为真时暂停计时，`visibilitychange` 恢复后立即补一次。
5. **失败熔断**：连续 3 次请求失败即停止并展示错误 + trace_id，禁止无限重试。
6. **销毁清理**：`onUnmounted` 必须清除定时器，属硬性验收项（Vitest 覆盖）。

## 15. 稳定性规范（每个页面必须遵守）

- 三态：loading / empty / error 每页显式处理，`PageTable` 内置
- 写操作：按钮 loading 防重复提交；成功提示 + 失败信封 message 直出
- 路由懒加载：每模块 `() => import()`，首屏只载骨架 + 登录
- 错误提示永远带 trace_id 尾缀，前端问题可与后端日志互查

### 15.1 错误码处理白名单（`shared/utils/error-map.ts`）

错误处理不采用「全量映射」，只对**需要改变 UI 行为**的错误码做特殊处理；其余一律 message 直出 + trace_id。白名单如下（错误码取值与语义唯一来源 `common/errors/codes.py`，**前端不得新增、改名或重定义错误码**）：

| 错误码 | 语义 | 前端动作 |
|---|---|---|
| `B0001` | 参数校验失败 | 表单行内标红 + 聚焦本地 `rules` 首个未通过项；不弹全局 toast（**后端 422 无字段级明细，不得依赖**） |
| `B0002` | 未认证 | 清登录态 → `/login?redirect=当前路由` |
| `B0003` | 无权限 | 403 提示，不自动回首页重试 |
| `B0004` | 资源不存在 | 404/空态 + 返回列表入口 |
| `B0005` | 资源冲突（重复提交/并发） | 幂等提示「已提交，请勿重复操作」，不展示为错误 |
| `B0006` | 限流 / 研判队列满 | 「系统繁忙，稍后重试」+ 按 `Retry-After` 计算退避；**仅幂等 GET 允许由调用方（`usePolling`/按钮）重试 1 次，拦截器不自动重试** |
| `B0007` `B0008` `B0009` | 系统内部错误 / 网关错误 / 服务不可用 | 兜底文案 + trace_id，提供「重试」按钮 |
| `B0010` | 合规拦截 | 强提示「该操作被合规策略拦截」，**不提供重试**，引导人工确认 |
| `A2002` | 质检入参不合法（HTTP 422） | 同 `B0001`：表单行内标红，不弹全局错误 |
| `A2003` | 对话不可质检（未结束/全文未齐/无通话主数据） | 质检按钮置灰 + 悬浮说明原因，不发起请求 |
| `A2005` | 质检记录不存在（仅单通详情 GET，HTTP 404） | 同 `B0004`：详情空态 + 返回列表入口 |
| `A3004` | 检索相关性不足 | **保留码值语义**（rag-service 当前不抛此码，空结果走 `code 0` + 空数组）：结果区空态由 `items.length === 0` 判定，文案「未找到相关内容」+ 建议放宽条件 |
| `A5001` | 投诉工单不存在 | 按 **code** 跳 404 页（深链失效场景）；**不依赖 HTTP 404**——complaint-service 该失败实际返回 HTTP 200 |
| `A5002` | 工单状态不允许此操作 | 提示「状态已变更」+ 自动刷新详情 |
| `A5014` | 模式切换失败/已回滚 | 强警示（ElMessageBox）+ 重新拉取模式状态 |
| `A5015` `A5016` `A5017` | 转人审（Token 超限/超时/熔断） | 提示「已转人工审核」并跳复核队列，**不得展示为失败** |
| 其他 | 未列入 | 信封 message 直出 + trace_id 尾缀 |

> 验收方式：`error-map.ts` 单测逐条覆盖上表；未列入的码必须走默认分支，新增映射需同步本表。

## 17. 新模块接入清单（验证可扩展性的标尺）

加一个业务模块只需 **3 步 + 1 项验证**，不动底座：

### 19.5 批次 2：轮询内核（最容易做错的一批）

**关键决策：shared 只收「调度引擎」，业务间隔策略留在模块。**
complaint 的「按 `task_status` 退避 + 等待人工固定 5s」属于业务策略，一旦塞进 shared 就让共享层出现业务语义，违反 §7 铁律 3。

```ts
// shared/composables/usePoller.ts（实现已定稿）
function usePoller<T>(options: {
  poll: () => Promise<T>
  isTerminal: (v: T) => boolean                        // 终态谓词
  nextInterval?: (v: T, current: number) => number     // 间隔由调用方决定（含退避），默认恒定 intervalMs
  intervalMs?: number                                  // 默认 3000
  maxFailures?: number                                 // 默认 3
  onTerminal?: (v: T) => void
  onError?: (message: string, trace?: string) => void
}): {
  isPolling: Ref<boolean>; isStopped: Ref<boolean>; lastResult: Ref<T | null>
  error: Ref<string | null>; errorTrace: Ref<string | null>
  start: () => Promise<void>; stop: () => void; pollNow: () => Promise<void>
}
```

改造方式：

- `modules/complaint/composables/usePolling.ts`：**文件名与返回形状不变**，内部改为调用 `usePoller`，把 `TERMINAL_TASK_STATUS` / `WAITING_HUMAN_TASK_STATUS` 与退避阶梯作为 `isTerminal` / `nextInterval` 传入；`status` 改为 `computed(() => poller.lastResult?.task_status ?? null)`（终态值也会写入 `lastResult`）——`ComplaintDetail` 零改动。
- `modules/rag/composables/useKbIngestPolling.ts`：改为纯参数转译适配器（`intervalMs` 3000 / `maxFailures` 5），返回面裁剪为原 6 个字段。

**两处实现层面的修正（评审 §19.5 原方案时未预见，实现期以证据推翻）**：

1. **取消 `resumeBehavior` 选项，两份统一为「恢复可见 → 补一次 + 重排定时器」。** 原方案认为 complaint 是「只补一次」的有意设计；实测其 `handleVisibilityChange` 只调 `pollNow()`（tick 内部不重排），恢复后定时器已不存在，非终态任务会静默停止轮询——这是缺陷而非语义差异。保留该选项只会把 bug 参数化。
2. **`start()` 允许在 `stop()` 之后重启。** 原 complaint 实现 `if (isStopped.value) return`，导致 `complaintId` 变化时的 `stop(); start()` 重启路径永远无效（`watch` 里 stop 后立即 start 必然被拦）。现由引擎统一：`start()` 重置 `isStopped`，两个模块共用同一语义。

# 附录 A · 概念对照（面向不熟悉 AI/后端的前端开发者）

> 只解释**前端会接触到**的概念；不必理解 LangGraph/Langfuse 内部实现。前端的工作边界是：**触发任务 → 展示状态 → 展示结果 → 提交人工决策**，其余都在后端。

| 术语 | 后端含义 | 前端怎么用 |
|---|---|---|
| 信封（envelope） | 所有接口统一外壳 `{code,message,data,trace_id}` | 只在 `shared/request.ts` 处理一次，业务代码只拿 `data` |
| `trace_id` | 一次请求的全链路身份证，串起网关→服务→LLM 调用 | 错误提示附后 8 位；`TraceIdText` 组件可复制，用于查后端日志 |
| 服务（service） | 按业务拆的独立进程（complaint/qc/rag…） | 前端**只认网关一个入口** `/api`，不关心背后是哪台服务 |
| 研判 / judge | 投诉单的核心处理任务，LangGraph 跑多个节点，耗时数十秒 | 点击后 `POST .../judge`（长超时）→ 轮询 `/status` → 终态拉 `/verdict`；**不要在前端拼节点逻辑** |
| LangGraph 节点 | 研判流程中的一个处理步骤（如查证据、判责、生成结论） | 只用来画「进度时间线」，节点名/状态由 `/status` 返回，前端不自造文案 |
| 证据包（evidence） | 研判结论引用的依据（含 RAG 源文档 ID） | 列表/卡片展示 + 可点回源文档；字段来自详情响应，不自造 |
| 转人工（pending_review） | 系统主动把工单交给人工，**是正常业务结果**，不是失败 | 展示为「待复核」正向状态；`A5015/A5016/A5017` 不得报错（§15.1） |
| RAG 召回（chunk/score/page） | 检索命中的文本片段、相似度、原文页码 | 检索测试台结果卡片；`score` 只展示不二次计算 |
| 规则分 / LLM 复核分 | 质检的两套打分：规则命中 vs 大模型复核 | 双轨展示，不合并成一个数，避免误导 |
| Agent logs | 研判过程中各节点的调试日志 | 折叠面板展示，面向管理员/训练师；默认不干扰业务用户 |
| 限流 / 熔断 / fallback | 后端保护机制：拒绝过多请求、失败快速返回、降级到备用模型 | 前端只感知 `B0006`/`B0010` 类错误码，按 §15.1 退避与提示 |
| Checkpointer 断点 | 后端保存任务执行进度，可恢复 | **前端不感知**；刷新页面用业务 ID（complaint_id/session_id）重新查询即可 |
| 幂等 | 同一操作重复提交不会产生两条数据 | 前端仍必须按钮防重（`B0005` 是兜底，不是方案） |

> 记住一条：**前端不复制后端的业务规则**。凡是"这个状态该显示什么/能不能操作"的判断，优先看后端返回的字段与错误码；后端没给的规则，不要在前端自创。
