
## 第二段提示词 ======================================================================================
/opsx-propose data-platform-min-loop

按仓库默认 spec-driven 创建 change「data-platform-min-loop」。本请求只生成 proposal、delta specs、design、tasks，不写业务代码，不执行 apply。

目标：数据中台最小闭环。只把三块已经存在的系统用同一套假数据串真：RAG 多模态混合检索（rag-service）、合规质检（qc-service）、智能投诉研判（complaint-service）。中台是薄底座。要求：真推送、真消费、真检索、真回流，外加一张极简案件快照。能不做的表和接口一律不做。不引入会打坏现有测试的行为。

读者不是后端。proposal、specs、design、tasks 用白话写清：谁发、谁收、复用哪条已有接口、字段来自哪张已有表、按什么顺序验收。不要发明第二套工单、第二套字段、第二套通道。与现有 qc-source、投诉 API、RAG /kb/search 冲突时，以现有 openspec 为准。禁止修改 openspec/specs/00～07。

## 同一条剧本

全程使用同一个固定 case_id 常量（建议 MIN_LOOP_CASE_001），种子脚本、验收脚本、快照反查都用它，不在各处散落。

种子全是假数据，写入已有表，不建 ODS、不建 DWD、不做 ETL 任务表。固定一组假值（客户名「张*」、欠款固定一个数、逾期天数固定一个数），每次跑种子不漂移，否则验收对不上：
- public.cases：客户名用「张*」这种脱敏名、欠款、逾期天数。禁止明文手机号、身份证、银行卡
- public.call_records + public.dialog_turns：一通已结束通话。end_time 必须是 Asia/Shanghai 当天。duration_seconds 必须大于 0。对话主要中文，含一句能打到坐席高危规则 R11/R12/R13 的话（规则定义沿用 qc-service 现有规则，不重新定义）。质检服务禁止自己 INSERT call_records
- 种子和快照空行写在同一个脚本里、顺序执行：先 upsert 三张业务表（用 ON CONFLICT 或先 DELETE WHERE case_id 再 INSERT，保证重复执行不产生第二套主键），再 upsert 下面这张快照表的同一行。快照空行填 case_id、客户、欠款、逾期天数、通话 session_id、通话已结束，质检列和投诉列先空。脚本失败整体重跑，不留半截
- RAG 不重新入库。验收前保证知识库里至少有一份仓库已有的法规/禁语短文能被 search_regulations 命中（用 qc-service 已有禁语字典或 rag-service 已有样例，不新做解析器，不把通话录音或案件字段推进知识库）

## 顺序（必须按这个顺序，否则投诉读到的质检是空的）

1. 种子入库，并写快照空行
2. 中台发布已有事件 etl.task.done。payload 里的 backfill_date 等于种子通话结束那天。qc-service 已有订阅，且 QC_AUTO_COMPLEMENT_AFTER_ETL 保持默认 true，然后自己 GET 已有的 qc-source 与 pending-qc，走已有离线质检
3. 中台订阅 qc.check.completed（走 QC_REDIS_DB，见末尾）。收到该事件且确认 qc_records 已落库后，中台再 HTTP 调用已有 POST /api/v1/complaints。禁止轮询、禁止 sleep 等待、禁止在未收到事件前就推投诉
4. 投诉创建沿用现有触发方式（现有接口已有的 run_graph=true 传参，不新做触发器，不改接口契约）。研判通过下面的进程内桥读取同一案件、同一通对话、刚出的质检、以及真 RAG
5. 质检完成事件和投诉回写更新同一行快照

禁止 data-platform 用 HTTP POST 调用 qc。禁止用 qc.complaint.suspected 自动新建投诉工单。

## 投诉怎么创建

- POST 体只带 complaint_text 和 case_id。case_id 必须是种子那条案件
- 禁止把通话 session_id 写入投诉创建请求的 session_id。该字段在现有代码里是研判会话号，填了会和通话号混成一个
- 不要修改 complaint_service.create。现有实现在传入 case_id 时会沿用它作为工单号。闭环接受「这个路径上 complaint_id 与 case_id 相同」。重复 POST 同一个 case_id 不得产生第二张工单，靠这个现有行为，不要另做幂等表，不要借机重写创建函数

## 检索与进程内桥

默认 USE_MOCK_MCP 保持 true（complaint-service 进程级开关，不是单请求级）。现有投诉演示和单测继续走 Mock。闭环验收时整个 complaint-service 进程切 USE_MOCK_MCP=false。禁止实现独立 MCP 网关，禁止要求 MCP_GATEWAY_URL。图节点仍然只调 mcp.call，禁止节点 import 其它服务，禁止投诉进程直接查 call_records。

只为研判图真正调用的工具补进程内桥：
- rag_kb：search_regulations、search_response_templates。桥已存在，打到 rag-service 已有 POST /api/v1/kb/search。质检词库继续 GET /api/v1/sensitive-words/current.dict。不改混合检索、重排、OCR、ASR、分块、Gradio
- business_ticket：query_case_info 返回形状对齐现有 fixture（case_id、overdue_amount、overdue_days、customer_name、product_type、create_time；repayment_records 允许空数组）。数据来自这张快照或 public.cases 的同一行，客户名保持脱敏。query_history_tickets、query_history_complaints 没有历史时返回空列表，不要 500，不要为历史新做表
- call_qc 的 query_call_asr：质检服务禁止实现这个工具，不要加到 qc-service。桥只用案件号向中台快照查出通话 session_id，再 GET 已有 qc-source，组装成投诉现有 fixture 的形状：列表，元素含 call_session_id、call_duration（大于 0）、asr_text_with_timestamp（含 speaker 和中文 text）。快照查不到 session_id、或 qc-source 查不到记录，都返回空列表，不要 500（与 query_qc_violations 一致）。不要改 evidence_call_qc 节点
- call_qc 的 query_qc_violations：图只传 case_id。桥先用快照查出通话 session_id，再 GET 已有 /api/v1/qc/records/{session_id}，整理成列表。不要改这个节点，不要给质检新增接口。查不到记录时返回空列表，不要 500
- data_platform：write_session、write_human_review_truth。现有节点入参只有研判 session_id、task_status、verdict。不要改 sample_backflow 节点。桥在投诉进程内用研判 session_id 反查 complaint_id 和 case_id，再更新快照上的投诉列。失败继续用已有重试和 csmp:backflow:retry，工单不得因此变成 500

图没有调用的工具保持现状，不要新做。

## 快照表

只新增一张表 dw.ads_case_loop，一行一个 case_id。列只许这些：case_id、客户名、欠款、逾期天数、通话 session_id、通话是否结束、qc_record_id、质检分数、风险、是否有高危告警、complaint_id、研判结论、任务状态、最后回流时间。

允许一个只读接口 GET /api/v1/data/snapshot/{case_id}，返回这一行，供上面的桥反查 session_id 使用。case_id 上建唯一索引，保证一行一案件，重复 upsert 不插第二行。质检分数、风险、是否有高危告警三列沿用 qc_records 现有字段，不新造字段。「最后回流时间」用 Asia/Shanghai。不要报表 API，不要用户特征，不要日报，不要第二张宽表。

更新来源只有两个，重复投递只覆盖、不插第二行：
- 中台订阅已有 qc.check.completed，写质检列
- 上面两个回写工具写投诉列

旧质检规范里「不要在质检服务里做宽表」仍然有效。这张表只属于 data-platform。qc-service 里仍然禁止 ETL。

## 验收

一条脚本即可（放 data-platform/scripts/run_min_loop.py，可重复执行），不做页面：
- 同一 case_id 在种子、qc_records、投诉工单、dw.ads_case_loop 四处对得上
- 质检分数来自真开检，不是人手插入 qc_records
- 质检完成之后才研判。USE_MOCK_MCP=false 时，法规来自 rag-service 真检索；失败走已有降级，进程不崩
- 快照行能看到质检分数和回写的研判结论
- USE_MOCK_MCP=true 的现有投诉测试、现有质检主路径、现有 RAG 主路径保持通过

## 明确不做

- Vue、三合一前端、修改三个现有演示页、改造 Gradio
- 数仓分层、ODS/DWD/DWS 流水线、dw.dws_call_result、dw.ads_daily_report、dw.ads_user_features、特征工程、定时调度平台
- call-service、case-service、review-service 的业务功能
- 除这一张快照表和它的按 case_id 只读之外的新业务表、新管理接口、新错误码段
- 重做 RAG；把 query_call_asr 做到 qc-service；修改投诉图节点、sample_backflow、complaint_service.create
- 中台 POST 回调质检；质检事件自动建投诉单
- API 网关、独立 MCP 网关、Redis Stream 改造
- 真实呼叫中心、真实客户资料、日志里的明文证件号和完整手机号

## 安全

- 种子与快照中的电话、证件、卡号必须是假数据或脱敏值
- 回写只更新该 case_id 的那一行，不能改写别的案件
- 不新增对公网开放的任意写入。种子用运维脚本。不新做登录体系
- 内部 HTTP 沿用现有超时（5 秒）与重试（3 次）。失败要留下可查记录，不能假装成功
- 快照只读接口响应沿用统一格式 {code,message,data,trace_id}，不新增错误码段

## tasks 切法

每块大约 2 小时，写清要改的现有文件和禁止改动的文件：
1. 假数据写入已有三张业务表，并插入快照空行。结束时间是当天，时长大于 0。重复执行不产生第二套主键
2. 发布带 backfill_date 的 etl.task.done，质检真开检
3. 质检完成后再推投诉。只传 complaint_text 和 case_id。不改 create
4. 投诉进程内桥：案件、qc-source 对话形状、质检记录、已有 RAG 桥、回写反查 case_id。默认 Mock 不回归。不改图节点
5. qc.check.completed 与回写更新同一快照行
6. 按上面的顺序做一条剧本验收，并确认旧测试仍绿

capabilities 只写增量：data-platform 最小闭环与这一张快照、complaint 上述工具的进程内真桥、qc 对已有 etl.task.done 的消费确认。不要重写 RAG 检索规格，不要重写质检规则引擎规格。
etl.task.done 和 qc.check.completed 都走质检已经在用的 Redis，库号是 QC_REDIS_DB（默认 3）。不要发到 0 号库。
