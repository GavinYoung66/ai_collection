#### 1.1.1 `rag.words.stale` 时钟（冻结 60s / 2h，不新造 Redis key）

- **权威版本：** Redis `rag:sensitive_words:version`（rag 更新词库后 INCR；`kb.sensitive_updated` 的 `payload.version` 与此相同）。
- **qc 已加载版本：** `qc:words:version`（成功拉取 `GET /api/v1/sensitive-words/current.dict` 并重建 AC 后回写）。
- **热加载 SLA：** 收到 `kb.sensitive_updated` 后 **60s 内** 完成拉取+重建（失败可重试，不改 60s）。
- **过期（发 `rag.words.stale`，Warning）：** 满足**任一**即告警：
  1. qc 拉取 current.dict **失败**且持续；或
  2. `now - last_success_load_at > 2h`（`last_success_load_at` = qc 最近一次成功重建 AC 的时间；进程内/日志时钟，**不是**新 Redis key）；或
  3. `qc:words:version != rag:sensitive_words:version` 且该不一致已持续 **>2h**。
- **`stale_hours` 字段** = `(now - last_success_load_at)` 的小时数。从未成功加载过时，从 qc 进程启动时刻起算（启动后仍无成功则与「失败且持续」同时成立）。

> 热刷新 60s 与过期 2h 是两套时钟，禁止把 60s 改成 2h 或反过来。

### 1.2 告警去重与抑制

| 机制 | 说明 |
|---|---|
| 去重 | 同一事件 5 分钟内只告警一次，后续抑制 |
| 聚合 | 同类事件按服务+错误码聚合，不逐条告警 |
| 恢复通知 | 告警恢复后发送恢复通知（resolved） |
| 升级 | Warning 级别持续 30 分钟未恢复 → 升级为 Critical |

## 二、三级告警体系

### 2.1 告警级别

| 级别 | 颜色 | 响应时效 | 通知对象 | 处置要求 |
|---|---|---|---|---|
| Critical | 红色 | 立即（<1 分钟） | 运维 on-call + 技术负责人 | 立即介入处理，5 分钟内响应 |
| Warning | 橙色 | 10 分钟内 | 运维 + 模块负责人 | 评估影响，30 分钟内处理 |
| Info | 蓝色 | 不催办 | 值班人员 | 记录备案，日常巡检关注 |

## 三、告警渠道

### 3.1 三路通知 + 持久化消费队列（Redis Stream）

| 渠道 | 接收者 | 适用级别 | 实现方式 |
|---|---|---|---|
| Redis Pub-Sub | 前端 / supervisor | Critical + Warning | PUBLISH `system.alert.raised`（仅实时推送，不保证 at-least-once） |
| Redis Stream（持久化队列） | supervisor / 运维消费端 | Critical + Warning | XADD `alert:stream`，消费成功 XACK；未 ACK 可重放 |
| 告警日志 | 运维 dashboard | 全部 | 写入 `audit_logs`（action=alert） |
| 邮件 | 运维 on-call | Critical | SMTP 发送告警邮件（Critical 兜底通道） |

> Redis Pub-Sub 仅实时推送，**不保证 at-least-once**（进程崩溃/断连即丢），不承载可靠性职责；告警可靠性由「audit_logs 落库 + Redis Stream 待消费队列」双保险承担（见 §3.2）。

### 3.2 Redis Pub-Sub 告警频道

| 频道 | 发布者 | Payload | 订阅者 |
|---|---|---|---|
| `system.alert.raised` | 各服务异常处理器 | `{alert_id, level, event, service, description, error_code, trace_id, ts}` | 前端 / supervisor / 运维 |
| `system.alert.resolved` | 各服务恢复探测 | `{alert_id, service, ts}` | 同上 |
| `qc.alert.raised` | qc-service | `{alert_id, session_id, call_id, level, evidence, trace_id, ts}` | 事后主管 / 运营前端（**不**含坐席通话页） |

**告警持久化与可靠投递（D3-1，消除单点丢消息）**：Pub-Sub 仅实时推送、不保证 at-least-once，可靠性不依赖 Pub-Sub。每次 Critical/Warning 告警触发时三动作并行：
1. PUBLISH `system.alert.raised`（即时推送，Payload 见上表）；
2. 写 `audit_logs`（action=alert_raised，字段见下方 §3.3）；
3. XADD 写 Redis Stream `alert:stream` 作为待消费队列（Payload 与 Pub-Sub 一致 `{alert_id, level, event, service, description, error_code, trace_id, ts}`），supervisor/运维消费端读取处理后 XACK；未 ACK 消息保留、可重新投递，实现不丢消息。

邮件（§3.1）作为 **Critical 兜底通道**：Pub-Sub 推送失败或消费端处理失败时仍可触达 on-call；`alert_resolved` 恢复事件同样 PUBLISH + 落 audit_logs（级别低，无需 Stream 保序）。

综上，Critical 告警具备「Pub-Sub（实时）+ audit_logs（留痕）+ Redis Stream（可重放）+ 邮件（兜底）」四重保险，无单点丢消息。

### 3.3 告警日志落库

所有告警事件写入 `audit_logs`：

| 字段 | 值 |
|---|---|
| user_id | NULL（系统触发，行为体记 detail.actor） |
| action | alert_raised / alert_resolved |
| resource_type | service_health / compliance / security |
| detail | JSON 含 alert_id, level, event, description, error_code, trace_id, actor="system" |
| create_time | 时间戳 |

## 六、日志规范

### 6.1 结构化 JSON 日志

所有日志使用 `structlog` 输出结构化 JSON，配置位于 `common/config/logging.py`。

### 6.2 日志级别

| 级别 | 适用场景 | 生产默认 |
|---|---|---|
| DEBUG | 开发调试、SQL 日志 | 不输出 |
| INFO | 正常业务流程、启动/关闭 | 输出 |
| WARNING | 业务异常、降级触发、阈值接近 | 输出 |
| ERROR | 系统异常、外部调用失败、告警事件 | 输出 + 告警 |

### 6.3 强制字段

| 字段 | 说明 | 示例 |
|---|---|---|
| timestamp | ISO 8601 带时区 | `2026-08-19T10:00:00+08:00` |
| level | 日志级别 | `ERROR` |
| logger | 模块名 | `call-service.dialog-engine` |
| trace_id | 全链路追踪 ID | `trace_01H8XK7P9M` |
| message | 日志消息 | `LLM 调用超时，触发熔断` |
| module | 业务模块 | `dialog-engine` |
| case_id | 案件 ID（可选） | `case_abc123` |
| session_id | 会话 ID（可选） | `sess_abc123` |

### 6.4 脱敏过滤器

适用范围 = **结构化日志输出前** + **业务表对话正文（`dialog_turns.text` / `call_records.summary`）落库前**，统一经 `common/security/mask.py` 过滤（PII 打码）。对话正文含客户自述身份证/手机号/银行卡号，原始敏感内容不入库；脱敏不可逆损失需在审计/训练用场景单独授权（原始走 AES-256-GCM 加密 + 角色授权解密，见 step4/01 §五）。

| 数据类型 | 脱敏规则 | 示例 |
|---|---|---|
| 手机号 | 中间 4 位打码 | `138****1234` |
| 身份证号 | 中间 11 位打码 | `110***********1234` |
| 金额 | 金额打码 | `****元` |
| 银行卡号 | 中间打码 | `6222****5678` |
| 密钥/Token | 完全遮蔽 | `****` |

> 违规脱敏即重大事故（openspec/specs/06 强制6）。

### 6.5 错误日志必须包含

- 模块名
- 入参摘要（脱敏后）
- 异常类型与完整堆栈
- 时间戳
- trace_id

## 七、X-Trace-Id 全链路追踪

### 7.1 传播路径

```
用户请求 → gateway 生成 trace_id
  → HTTP Header X-Trace-Id → 各服务
  → contextvars 存储 → 全链路透传
  → Redis Pub-Sub Payload → 跨服务事件
  → LLM 调用入参 → llm_call_logs.trace_id
  → 结构化日志 → 日志检索
  → audit_logs → 审计追溯
```

### 7.2 检索能力

- `GET /api/v1/audit-logs?trace_id=trace_xxx` → 单案件全流程串联查询
- 返回按时间排序的完整操作链：用户请求 → ASR → 意图 → LLM → Guardrails → TTS → 审计；质检为通话结束后的离线节点，不插在 TTS 前
- 每条记录含 service / action / detail / trace_id / create_time

## 八、审计追溯链

### 8.1 哈希链防篡改

`audit_logs` 表每条记录含 `seq BIGSERIAL` 全局单调序列号（PostgreSQL 序列保证并发下的全局顺序，解决 UUID 无序主键无全局顺序的问题）。每条记录的 `detail` JSONB 中存入 `prev_hash` 字段：

```
prev_hash = SHA256(prev_seq + prev_id + prev_action + prev_created_at)
prev_seq = 上一条记录的 seq（即小于当前 seq 的最大 seq 记录，以 ORDER BY seq 查询）
```

- 串链依据为 `seq` 单调序列（非 UUID 主键），并发写入下由数据库序列保证有序、无竞态
- 任何篡改会断链
- `scripts/verify_audit_chain.py` 每日扫描，按 seq 排序重算哈希链，断链即 Critical 告警
- 审计与业务数据**分级保留**（详见 §8.2）：audit_logs / llm_call_logs 保留 5 年；含 PII 正文的 dialog_turns / qc_records 按监管要求定保留期，到期匿名化归档或删除；录音文件（对象存储）单独定保留期——**不做"永不删除"，对齐个保法数据最小化与存储期限要求**

### 8.2 审计表清单

| 表 | 用途 | 关键字段 | 保留期 |
|---|---|---|---|
| llm_call_logs | LLM 调用全量审计（prompt/response 已脱敏，不含 PII 正文；prompt 内 RAG 上下文携带 source_id 标注，可溯源） | trace_id, prompt, response, confidence, status, temperature | 5 年 |
| audit_logs | 操作审计索引 + 告警记录（detail 已脱敏，不含 PII 正文） | user_id, action, resource_type, detail, prev_hash | 5 年 |
| dialog_turns | 逐轮对话（text 已 PII 打码；reasoning_encrypted 密文） | session_id, speaker（ai\|user；质检入站 ai→agent，见 step4/01）, text, reasoning_encrypted, intent_label | 按监管要求定保留期，到期匿名化归档或删除（不做"永不删除"） |
| qc_records | 质检结果（含质检上下文/正文引用） | session_id, compliance_score, violations, qc_result | 同 dialog_turns：按监管要求定保留期，到期匿名化归档或删除 |
| 录音文件（对象存储，call_records.record_url 指向） | 通话录音原始介质 | record_url, start_time | 单独定保留期，不与其他表混同；到期按监管口径删除或匿名化 |
| etl_task_logs | ETL 任务日志 | task_name, status, records_processed | 3 年 |

### 8.3 reasoning_encrypted 访问控制

- `dialog_turns.reasoning_encrypted` 仅限 role=admin 解密查看；
- 解密操作须记 audit_logs（action=reasoning_decrypt）；
- 加密算法 AES-256-GCM，密钥经 docker secrets 注入。

## 九、可观测性仪表盘

### 9.1 仪表盘规划（MVP）

| 仪表盘 | 数据源 | 核心指标 |
|---|---|---|
| 服务健康总览 | /health 端点 | 7 服务状态灯 |
| 外呼实时监控 | call_records + Redis | 并发数 / 成功率 / 转人工率 |
| LLM 调用监控 | llm_call_logs | QPS / 延迟 P95 / 置信度 / 熔断状态 |
| 质检合规监控 | qc_records + sensitive_words | 扣分均值 / 红线/违规检出率 / 违规分布 |
| 知识库监控 | kb_documents + kb_chunks | 文档数 / 版本切换 / 检索命中率 |
| 告警事件流 | audit_logs | 告警列表 / 级别分布 / 恢复率 |

### 9.2 技术选型

| 组件 | 选型 | 说明 |
|---|---|---|
| 日志存储 | docker volume → JSON 文件 | MVP 不引入 ELK，structlog JSON 直接落文件 |
| 指标采集 | /health + /metrics 端点 | FastAPI middleware 计数 |
| 告警推送 | Redis Pub-Sub + 邮件 | 前端订阅 Pub-Sub 实时展示 |
| 仪表盘 | Vue3 + Element Plus | 复用前端框架，M3 起开发 |

> MVP 不引入 Prometheus/Grafana/ELK，以结构化日志 + Redis Pub-Sub + 前端仪表盘满足可观测性需求；后续可平滑接入 Prometheus。

## 十、验收标准

| 验收项 | 标准 |
|---|---|
| 全局异常捕获 | 0 原生 500 报错，所有异常封装为统一响应包 |
| 堆栈不泄漏 | 对外响应不含堆栈、路径、数据库信息 |
| 告警覆盖 | 17 项高危事件全部覆盖，Critical <1 分钟触达 |
| 告警去重 | 同事件 5 分钟内只告警一次 |
| 日志脱敏 | 0 条日志含明文手机号/身份证/金额 |
| trace_id 贯穿 | 单 trace_id 可串联全链路操作 |
| 审计链完整 | audit_logs 哈希链不断裂，每日扫描通过 |
| 健康检查 | 7 服务 /health 端点正常返回，连续 3 次失败触发告警 |
| 降级兜底 | 所有外部调用重试耗尽后有降级动作，无卡死 |
| 日志强制字段 | timestamp + level + logger + trace_id + message 全覆盖 |
