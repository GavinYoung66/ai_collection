## 一、告警事件目录

### 1.1 五类高危事件（openspec/06 强制4）

| 类别 | 事件 | 触发条件 | 级别 | 对应错误码 |
|---|---|---|---|---|
| LLM 异常 | LLM 批量失败 | 5 分钟内 ≥5 次连续失败 | Critical | A1013 |
| LLM 异常 | LLM 高频超时 | P95 > 800ms 持续 5 分钟 | Critical | A1013 |
| LLM 异常 | 熔断触发 | pybreaker OPEN 状态变更 | Critical | — |
| LLM 异常 | 置信度持续偏低 | 10 分钟内平均 confidence < 0.6 | Warning | A1010 |
| 合规事件 | 合规拦截触发（前置） | L2 前置校验命中敏感词 | Warning | B0010 |
| 合规事件 | 合规拦截触发（后置） | L4 后置校验命中违规内容 | Critical | B0010 |
| 合规事件 | 敏感词库热刷新失败 | qc-service 拉取词库超时/解析失败 | Warning | A3003 |
| 安全事件 | 异常访问 | 同 IP 1 分钟内 >100 次请求 | Critical | B0006 |
| 安全事件 | SQL 高危操作 | 未授权 DDL / 全表 DELETE / DROP | Critical | B0009 |
| 安全事件 | 审计链断链 | audit_logs 哈希链校验失败 | Critical | — |
| 系统事件 | 接口报错暴涨 | 5 分钟内 5xx 错误率 >10% | Critical | B0007/B0008 |
| 系统事件 | 并发触达上限 | 外呼并发持续 >48 路（接近 50 上限） | Warning | A1012 |
| 系统事件 | DB 连接池耗尽 | 连接池使用率 >90% | Critical | B0007 |
| 系统事件 | Redis 内存告警 | used_memory > 1.8GB（2GB 上限 90%） | Warning | — |
| 数据中台 | ETL 同步失败 | ETL 任务重试 3 次仍失败 | Warning | A7005 |
| 数据中台 | 策略回流失败 | 策略版本切换回滚 | Warning | A7006 |
| 服务健康 | 服务下线 | 任一服务健康检查连续 3 次失败 | Critical | — |

### 1.2 告警去重与抑制

| 机制 | 说明 |
|---|---|
| 去重 | 同一事件 5 分钟内只告警一次，后续抑制 |
| 聚合 | 同类事件按服务+错误码聚合，不逐条告警 |
| 恢复通知 | 告警恢复后发送恢复通知（resolved） |
| 升级 | Warning 级别持续 30 分钟未恢复 → 升级为 Critical |

## 二、三级告警体系

### 2.1 告警级别

| 级别 | 颜色 | 响应时效 | 通知对象 | 处置要求 |
|---|---|---|---|---|
| Critical | 红色 | 立即（<1 分钟） | 运维 on-call + 技术负责人 | 立即介入处理，5 分钟内响应 |
| Warning | 橙色 | 10 分钟内 | 运维 + 模块负责人 | 评估影响，30 分钟内处理 |
| Info | 蓝色 | 不催办 | 值班人员 | 记录备案，日常巡检关注 |

### 2.2 告警内容规范

每条告警必须包含：

```json
{
  "alert_id": "alert_<ulid>",
  "level": "Critical",
  "category": "llm_anomaly",
  "event": "llm_batch_failure",
  "service": "call-service",
  "description": "LLM 5分钟内连续失败 7 次，已触发熔断",
  "error_code": "A1013",
  "trace_id": "trace_xxx",
  "metrics": {
    "failure_count": 7,
    "window": "5min",
    "p95_latency_ms": 1200
  },
  "action": "已切换 RuleBasedScriptEngine 兜底",
  "ts": 1724054400
}
```

## 三、告警渠道

### 3.1 三路通知

| 渠道 | 接收者 | 适用级别 | 实现方式 |
|---|---|---|---|
| Redis Pub-Sub | 前端 / supervisor | Critical + Warning | PUBLISH `system.alert.raised` |
| 告警日志 | 运维 dashboard | 全部 | 写入 `audit_logs`（action=alert） |
| 邮件 | 运维 on-call | Critical | SMTP 发送告警邮件 |

### 3.2 Redis Pub-Sub 告警频道

| 频道 | 发布者 | Payload | 订阅者 |
|---|---|---|---|
| `system.alert.raised` | 各服务异常处理器 | `{alert_id, level, event, service, description, error_code, trace_id, ts}` | 前端 / supervisor / 运维 |
| `system.alert.resolved` | 各服务恢复探测 | `{alert_id, service, ts}` | 同上 |
| `qc.alert.raised` | qc-service | `{alert_id, session_id, call_id, level, evidence, trace_id, ts}` | 前端 / 坐席服务 / supervisor |

### 3.3 告警日志落库

所有告警事件写入 `audit_logs`：

| 字段 | 值 |
|---|---|
| user_id | 系统（system） |
| action | alert_raised / alert_resolved |
| resource_type | service_health / compliance / security |
| detail | JSON 含 alert_id, level, event, description, error_code, trace_id |
| create_time | 时间戳 |

## 五、健康检查

```json

  "status": "healthy",
```

## 六、日志规范

### 6.1 结构化 JSON 日志

所有日志使用 `structlog` 输出结构化 JSON，配置位于 `common/config/logging.py`。

### 6.2 日志级别

| 级别 | 适用场景 | 生产默认 |
|---|---|---|
| DEBUG | 开发调试、SQL 日志 | 不输出 |
| INFO | 正常业务流程、启动/关闭 | 输出 |
| WARNING | 业务异常、降级触发、阈值接近 | 输出 |
| ERROR | 系统异常、外部调用失败、告警事件 | 输出 + 告警 |

### 6.3 强制字段

| 字段 | 说明 | 示例 |
|---|---|---|
| timestamp | ISO 8601 带时区 | `2026-08-19T10:00:00+08:00` |
| level | 日志级别 | `ERROR` |
| logger | 模块名 | `call-service.dialog-engine` |
| trace_id | 全链路追踪 ID | `trace_01H8XK7P9M` |
| message | 日志消息 | `LLM 调用超时，触发熔断` |
| module | 业务模块 | `dialog-engine` |
| case_id | 案件 ID（可选） | `case_abc123` |
| session_id | 会话 ID（可选） | `sess_abc123` |

### 6.4 脱敏过滤器

日志输出前经 `common/security/mask.py` 过滤：

| 数据类型 | 脱敏规则 | 示例 |
|---|---|---|
| 手机号 | 中间 4 位打码 | `138****1234` |
| 身份证号 | 中间 11 位打码 | `110***********1234` |
| 金额 | 金额打码 | `****元` |
| 银行卡号 | 中间打码 | `6222****5678` |
| 密钥/Token | 完全遮蔽 | `****` |

> 违规脱敏即重大事故（openspec/specs/06 强制6）。

### 6.5 错误日志必须包含

- 模块名
- 入参摘要（脱敏后）
- 异常类型与完整堆栈
- 时间戳
- trace_id

## 七、X-Trace-Id 全链路追踪

### 7.1 传播路径

```
用户请求 → gateway 生成 trace_id
  → HTTP Header X-Trace-Id → 各服务
  → contextvars 存储 → 全链路透传
  → Redis Pub-Sub Payload → 跨服务事件
  → LLM 调用入参 → llm_call_logs.trace_id
  → 结构化日志 → 日志检索
  → audit_logs → 审计追溯
```

### 7.2 检索能力

- `GET /api/v1/audit-logs?trace_id=trace_xxx` → 单案件全流程串联查询
- 返回按时间排序的完整操作链：用户请求 → ASR → 意图 → LLM → 质检 → TTS → 审计
- 每条记录含 service / action / detail / trace_id / create_time

## 八、审计追溯链

### 8.1 哈希链防篡改

`audit_logs` 表每条记录的 `detail` JSONB 中存入 `prev_hash` 字段：

```
prev_hash = SHA256(上一条记录的 id + action + created_at)
```

- 任何篡改会断链
- `scripts/verify_audit_chain.py` 每日扫描，断链即 Critical 告警
- 审计日志仅归档永不删除，以备 5 年合规审计追溯

### 8.2 审计表清单

| 表 | 用途 | 关键字段 | 保留期 |
|---|---|---|---|
| llm_call_logs | LLM 调用全量审计 | trace_id, prompt, response, confidence, status | 5 年 |
| audit_logs | 操作审计 + 告警记录 | user_id, action, resource_type, detail, prev_hash | 5 年 |
| dialog_turns | 逐轮对话 | session_id, speaker, text, reasoning_encrypted, intent_label | 5 年 |
| qc_records | 质检结果 | session_id, compliance_score, violations, qc_result | 5 年 |
| etl_task_logs | ETL 任务日志 | task_name, status, records_processed | 3 年 |

### 8.3 reasoning_encrypted 访问控制

- `dialog_turns.reasoning_encrypted` 仅限 role=admin 解密查看；
- 解密操作须记 audit_logs（action=reasoning_decrypt）；
- 加密算法 AES-256-GCM，密钥经 docker secrets 注入。

## 九、可观测性仪表盘

### 9.1 仪表盘规划（MVP）

| 仪表盘 | 数据源 | 核心指标 |
|---|---|---|
| 服务健康总览 | /health 端点 | 7 服务状态灯 |
| 外呼实时监控 | call_records + Redis | 并发数 / 成功率 / 转人工率 |
| LLM 调用监控 | llm_call_logs | QPS / 延迟 P95 / 置信度 / 熔断状态 |
| 质检合规监控 | qc_records + sensitive_words | 扣分均值 / 拦截率 / 违规分布 |
| 知识库监控 | kb_documents + kb_chunks | 文档数 / 版本切换 / 检索命中率 |
| 告警事件流 | audit_logs | 告警列表 / 级别分布 / 恢复率 |

### 9.2 技术选型

| 组件 | 选型 | 说明 |
|---|---|---|
| 日志存储 | docker volume → JSON 文件 | MVP 不引入 ELK，structlog JSON 直接落文件 |
| 指标采集 | /health + /metrics 端点 | FastAPI middleware 计数 |
| 告警推送 | Redis Pub-Sub + 邮件 | 前端订阅 Pub-Sub 实时展示 |
| 仪表盘 | Vue3 + Element Plus | 复用前端框架，M3 起开发 |

> MVP 不引入 Prometheus/Grafana/ELK，以结构化日志 + Redis Pub-Sub + 前端仪表盘满足可观测性需求；后续可平滑接入 Prometheus。

## 十、验收标准

| 验收项 | 标准 |
|---|---|
| 全局异常捕获 | 0 原生 500 报错，所有异常封装为统一响应包 |
| 堆栈不泄漏 | 对外响应不含堆栈、路径、数据库信息 |
| 告警覆盖 | 17 项高危事件全部覆盖，Critical <1 分钟触达 |
| 告警去重 | 同事件 5 分钟内只告警一次 |
| 日志脱敏 | 0 条日志含明文手机号/身份证/金额 |
| trace_id 贯穿 | 单 trace_id 可串联全链路操作 |
| 审计链完整 | audit_logs 哈希链不断裂，每日扫描通过 |
| 健康检查 | 7 服务 /health 端点正常返回，连续 3 次失败触发告警 |
| 降级兜底 | 所有外部调用重试耗尽后有降级动作，无卡死 |
| 日志强制字段 | timestamp + level + logger + trace_id + message 全覆盖 |
