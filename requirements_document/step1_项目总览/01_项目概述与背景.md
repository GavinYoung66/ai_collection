## 项目背景

传统贷后催收在信用卡、消费贷、小微贷逾期场景下面临四类瓶颈：人力成本高且话术随坐席波动、合规风险不可控、质检只能抽样、策略迭代依赖人工经验。本项目建设 7 个垂直 AI 子系统，覆盖分案、外呼、质检、知识库、投诉研判、复盘培训、数据中台全链路，以大模型 + RAG + 向量库 + RTC 实时语音为核心能力，实现贷后催收的合规化、全量化、数据闭环化作业。

MVP 聚焦"轻量案件 AI 外呼 + 全量质检 + 知识库 + 智能分案 + 投诉研判 + 复盘培训 + 数据中台"最小闭环；Text2SQL、在线微调、模拟对打培训等扩展能力推迟到 M5 之后。

## 项目目标

1. 提升外呼作业效率，AI 承接轻量案件，人工坐席聚焦高对抗案件；
2. 全流程合规管控，所有 AI 输出经 Guardrails 前后置校验；
3. 通话全量 AI 质检，替代抽样人工质检；
4. RAG 混合检索实现账单、政策、标准答案实时查询；
5. 三维风险打分驱动智能分案与策略匹配；
6. 通话自动复盘、优质话术沉淀、坐席画像自动生成；
7. 投诉异议自动研判与风险标签输出；
8. 统一数据中台沉淀业务指标、会话日志、模型日志，支撑策略回流。

## 非目标（MVP 不含）

1. 不做通用大模型训练，基于 qwen-plus / bge-large-zh-v1.5 基座做应用层开发；
2. 不替代全部人工坐席，AI 作为前置处理与辅助，高对抗案件转人工；
3. 不绕过监管合规要求，所有 AI 输出必须经过护栏校验；
4. 不做多租户，MVP 单组织运行，全表不加 `tenant_id`，将来需要再迁移；
5. 不做移动端 / 小程序 / 对外开放 API；
6. 不做在线微调、模拟对打培训、高度自定义报表；
7. Text2SQL 推迟至 M5 之后，MVP 期间账单查询走 RAG + 结构化接口。

### 接口与数据约定

- 统一响应包：`{ "code": "0", "message": "...", "data": ..., "trace_id": "..." }`，`code` 为字符串、`"0"` 表示成功；详见 step5/02；
- 公共字段：所有业务表必须含 `id`、`create_time`、`update_time`、`is_delete` 四个公共字段，软删统一走 `is_delete` CHAR(1)（'0'=正常, '1'=已删除）；详见 step4/01；
- 数据模型以 DDL 为单一事实源，Pydantic 模型对齐 DDL，CI 双向校验脚本防止漂移；详见 step4/01；
- 错误码以 step6/01 全集为唯一基线（A1xxx~A7xxx + B，共 84 条含 DD 扩展码），子系统新增错误码须经评审收录，禁止私自编号；详见 step6/01。

### 置信度与降级门控

- LLM 输出 confidence < 0.7：禁止直接回复用户，走兜底或转人工；
- RAG 检索 score < 0.6：判定知识库无匹配，标记降级、不自由作答；
- 意图识别 confidence < 0.6：记为 uncertain，不阻断流程但落记录；
- LLM 超时 / 熔断 / 检索为空：按预设话术 → FAQ → 合规兜底分级降级；详见 step3/03。

### 外呼业务口径

- 外呼时段 08:00–21:00，非时段禁止外呼；
- 同用户每日 ≤ 3 次，重试间隔 ≥ 30 分钟，最大重试 3 次；
- 并发上限 50 路；
- 单通话最大 15 轮，第 13 轮触发关键要素判断分支。

**实现深度：** 仓库当前深做切片为 `rag-service`(8002) 与 `complaint-service`(8006)；`data-platform` / `qc-service` / `call-service` / `case-service` / `review-service` 在未达里程碑前可为 health 占位，**不得**对外表述为七大业务功能均已生产完备。
