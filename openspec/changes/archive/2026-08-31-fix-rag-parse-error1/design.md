## Context

针对 V5 当前三个缺陷（详见 proposal.md「What Changes」）：混合检索去重失效导致同内容重复 5–6 条；`.xlsx` 在 `data_only=True` 下把公式单元格读成 `None` 造成整表判空 → 分块数归零 → A3002；音频 ASR 在已配置可用 Key 时仍误报「DASHSCOPE_API_KEY not configured」→ A3001。本设计仅说明修复思路，不涉及具体实现代码。

## Goals / Non-Goals

**Goals：**
- 检索：在既有 RRF 融合 + doc_id 去重基础上叠加**内容级去重**，并让重排对中文查询具备区分度，保证排序收敛、Top1 含答案上下文。
- 解析：`.xlsx` 读取兼容公式单元格，避免"有数据的表被判空"。
- ASR：正确判定所选 Provider 的 Key 可用性，已配置 Key 时正常转写。
- 全部修复不改变既有接口入参/出参、错误码（A3001/A3002）、双索引契约与双闸门兜底。

**Non-Goals：**
- 不做大范围重构、不引入新业务能力、不新增能力/配置开关（除非确为既有契约遗漏，且需在 spec 中体现）。
- 不改动主库 `openspec/specs/**` 与其他归档变更。
- 不实现新增的检索/排序算法变体（如新模型选型）、不实现语义级 VAD/说话人识别。

## Decisions

### 决策 1：内容级去重（缺陷 1）
- **方案**：在 RRF 融合输出后的去重阶段，先按 doc_id 去重（既有），再对 content 规范化（去空白、统一大小写/全半角标点）后做内容相似比较，相同/高度相似（如文本归一化后相等或仅格式差异）只保留排序靠前一条。
- **理由**：仅按 doc_id 去重无法覆盖"多个不同 doc_id 的文档内容一字不差"这一根因；在输出去重阶段做内容去重代价小、对既有 RRF 分计算零侵入。
- **替代方案**：入库阶段就拒绝重复文档 / 按 content 建唯一约束。副作用：会改变"重复文档允许入库"的既有行为，并增加入库耦合，不符合"不做大范围重构"约束，故不选。

### 决策 2：中文重排区分度（缺陷 1）
- **方案**：重排输入侧对中文 query/chunk 计算相似度时，避免仅依赖 `\w+` 切词；改用**字符级 n-gram / 分词级** overlap 计算，保证不同候选分出差值；mock 环境同步适配（否则本地冒烟仍恒 0.8）。
- **理由**：`\w+` 对中文整串只切 1 个 token，使所有候选 overlap=0 → 恒定 0.8，无区分度。字符级特征对中文稳定且无额外模型依赖。
- **替代方案**：引入 jieba 等分词库 / 直接启用真实 `bge-reranker-large`。jieb 引入新依赖、真实 reranker 需要模型与算力，作为可选项说明；本变更默认走字符级方案以保证离线可跑。

### 决策 3：`.xlsx` 公式单元格兼容（缺陷 2）
- **方案**：读取单元格时对 `data_only=True` 结果为 `None` 的公式单元格，回退用 `data_only=False` 读取公式字符串/原始值作为文本；仅当全表无可提取文本时才判空（A3002）。
- **理由**：`data_only=True` 依赖公式缓存结果，未用 Excel/WPS 保存过的文件根本没有缓存，导致有数据的表被读成空。回退读取成本低、不改变既有 sheet/表头/行切块/前辍/跳过空行行为。
- **替代方案**：改用 pandas 或 xlrd。引入新依赖且改变解析来源，不符合约束，不选。

### 决策 4：ASR Key 可用性判定（缺陷 3）
- **方案**：DashScope ASR Provider 在调用前读取 `DASHSCOPE_API_KEY`（与已配置的千问 DashScope Key 对齐），非空即视为可用并调转写；为空才抛 A3001，且错误信息明确缺失项。是否降级仍由既有 `KB_OCR_ASR_DEGRADED_KEEP_TEXT` 控制。
- **理由**：根因是"环境已配可用千问/DeepSeek Key，但 ASR 判空"，属于 Key 读取/判定口径不一致。修复判定口径即可，不改变既有转写管线与降级契约。
- **替代方案**：改走 whisper / 引入 mock ASR。需新增模型依赖或独立 mock 服务，属较大改动，作为可选方案记录，非本变更默认。

## Risks / Trade-offs

- **[内容级去重可能误删语义相近但确有差异的内容]** → 采用"归一化后相等或仅格式差异"的保守判定，避免过度合并；内容级去重仅作用于输出阶段，不降低召回。
- **[中文重排字符级特征与真实语义可能存在偏差]** → 作为离线可跑的确定性方案，保证排序收敛与可测试性；后续可平滑替换为真实 reranker（属 Backlog，不阻塞本变更）。
- **[`.xlsx` 公式回退可能读入公式字符串而非计算值]** → 文本化入库以"可读、可检索"为目标，公式字符串仍具辨识度；真实计算值依赖用户侧用 Excel 保存（文档注明）。
- **[ASR 判定口径修复可能依赖用户实际配置的 Key 变量名]** → 涉及 `.env` 配置项命名，需在 apply 阶段按容器实际 env 校准；若同一 DashScope 账号则复用 `DASHSCOPE_API_KEY`。

## Migration Plan

- 部署：改代码后用 `docker compose up -d --build` 重建受影响服务（rag-service，及 dev 环境涉及的 rerank/embedding mock）；`env_file: .env` 的配置变更需重启生效。
- 回滚：各修复为独立小改动，逐项可回滚；因不改既有接口/错误码契约，回滚仅需恢复对应源文件并重建。
- 兼容：不迁移数据；检索/入库行为修复后既有数据无需重灌。

## Open Questions

- 若已配置的千问 Key 与 `DASHSCOPE_API_KEY` 命名不一致（如为 `QWEN_API_KEY`），是否需在 `.env` 统一映射为 `DASHSCOPE_API_KEY`，或在 ASR 判定中兼容读取。该问题不影响 spec 与任务拆分（spec 已按"配置可用 Key 即可用"定义），可在 apply 时按容器实际环境校准。
