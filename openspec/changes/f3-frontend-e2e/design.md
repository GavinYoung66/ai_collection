# Design

## D1. 为什么选 Playwright

| 候选 | 判断 |
|---|---|
| **Playwright**（选定） | 原生浏览器协议、自动等待（消除手工 sleep）、`trace` 回放可定位时序问题、CI 官方镜像成熟、单浏览器可裁剪 |
| Cypress | 同源限制与多标签弱，对本项目「子路径 `/admin/` + 网关穿透」场景更易受限，且体积更大 |
| 继续用 jsdom 单测 | 已证明无法覆盖：无真实布局、无懒加载 chunk 异步、无动画帧与事件阶段——F2 导航缺陷正是漏网例证 |

结论：交互时序类缺陷必须用真实浏览器验证，jsdom 与静态门禁保留原有职责，不重叠。

## D2. 为什么 E2E 不连真实后端

- **目的单一**：本 change 只验证「交互行为与路由结果」，不验证「数据是否正确」。数据契约已由 F2 的 15 端点契约单测（`modules/qc/__tests__/api.spec.ts`）与接口级三角色矩阵 9/9 覆盖。
- **稳定性**：F2 期间后端容器多次因镜像漂移（qc-service 缺 jinja2）、RocketMQ 重启（replay 500 / 复核提交超时）造成与前端无关的失败；若 E2E 依赖真实链路，门禁会被环境噪音污染，失去「确定性」价值。
- **成本**：CI 拉起 5 服务 + 网关 + RocketMQ 的编排成本远高于收益。

实现方式：`page.route('**/api/**')` 返回固定信封（`{code,message,data,trace_id}`），按端点分派 fixture。

## D3. 覆盖率边界（明确不做什么）

只覆盖**壳层行为**：

1. 导航展开/折叠语义（含跨一级菜单切换）
2. 角色 × 路由的菜单可见性与守卫拦截
3. qc 关键按钮态（防连点、置灰条件、零扣分不渲染提交）

**不做**：数据字段渲染断言、分页正确性、错误码分支逐条覆盖、视觉回归（截图比对）。前三项属既有单测职责；视觉回归误报率高且维护成本大，暂不引入。

## D4. CI 策略

- 单浏览器 chromium（覆盖主流内核，减少 3 倍时长与不稳定面）
- `retries: 1`（仅吸收真实浏览器抖动，不允许掩盖稳定失败：连续两次失败仍红）
- `trace: 'on-first-retry'`、`screenshot: 'only-on-failure'`，产物上传供定位
- 与四道静态闸并行 job，**blocking**（失败即失败），不设 `continue-on-error`
- 门禁自测：验收时必须故意改坏一条断言并观察变红，防止 E2E 成为永不失败的摆设（F2 已暴露「`vue-tsc --noEmit` 空转」同类问题）

## D5. 必须包含 F2 缺陷的回归用例

导航用例 MUST 复刻触发路径：`点击其他一级菜单 → 点击带二级分组的父级 → 断言二级菜单在 1.5s 后仍处于展开态`。该断言直接锁死「展开后自动折叠」的时序回归；仅断言「点击后瞬间展开」不足以捕获该缺陷（缺陷表现为延迟折叠）。

同时锁定实现约束：父级标题导航必须发生在分组展开之后（`@open` 事件），不得在捕获阶段与 toggle 并发。

## D6. 与 SSOT 的关系

E2E 属研发基础设施，不涉及对外契约（路由/方法/信封/错误码/角色词表/网关超时）与架构决策变更，不满足《frontend/前端架构.md》允许修订的两类触发，因此**不改 SSOT**，仅在 proposal/tasks 中引用其既有约束作为断言依据。

## 风险

| 风险 | 处置 |
|---|---|
| chromium 内核下载体积大 | CI 缓存 `~/.cache/ms-playwright`；本地按需安装 |
| 用例依赖元素选择器，UI 改动易碎 | 优先走 role/text 语义选择器，避免 CSS 层级选择器；关键交互补 `data-testid`（仅测试属性，不影响产物行为） |
| 单测与 E2E 职责漂移 | D3 边界写死：E2E 不做数据断言，单测不做真实浏览器交互 |
